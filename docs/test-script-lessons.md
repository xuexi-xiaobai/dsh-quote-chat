# 测试脚本的反思：为什么会挂住，以及以后怎么不再犯

这份文档记录一次真实的事故，以及从里面提炼出的、后续必须执行的规则。

起因：一个探针脚本在做完所有动作之后**进程不退出**。Chrome 已经不再被控制，界面上什么都看不出来，
但 shell 拿不到提示符，后台任务永远不报告完成。我因此一直等，误以为测试还在跑。

---

## 工作流硬性约定（每次测试都必须遵守）

这一节是在多次被纠正之后补上的。以下每一条都被明确要求过，又被违反过，所以写成不可协商的约定。

### 约定一：默认不跑全量测试

**改一行 z-index、改一个样式值、改一个函数体 —— 跑对应的一个探针就够了。**

全量测试（22 个单元套件 + 3 个浏览器套件）只在以下时机跑：

- 一个功能完成、准备提交一个里程碑时
- 改动跨多个模块、无法预判影响面时
- 用户明确要求时

判断方法：**这次改动如果出错，最坏会坏在哪？** 只会坏在一个交互上，就测那一个交互。

反面案例：改一个 CSS 的 z-index，跑了 593 项单元 + 117 项浏览器检查，耗时数分钟，
而真正验证它的那个探针只要 4 秒。

### 约定二：窗口必须最大化

所有测量都依赖可读区域的高度：可读区间、屏幕上段落的数量、以及所有基于阈值的断言。
窗口不是最大化时，可读区域变矮，探针会报告"找不到可用段落"，这看起来像产品缺陷，其实是测量环境不对。

- `browser-serve.mjs` 启动时执行最大化并**读回状态确认**
- `harness.mjs` 即使在连接模式下也会检查并补齐最大化（已最大化时是一次空操作）
- 看到 `window did not maximise` 必须停下来修，不能继续测量

### 约定三：用常驻浏览器，不新开窗口

```sh
# 只启动一次，一直开着
node tools/browser-serve.mjs "<tokenised url>"

# 之后每一条命令都这样跑
QC_CDP=http://127.0.0.1:9222 node tools/probe-xxx.mjs "<url>"
```

不要为了"干净状态"而杀掉常驻浏览器重开。需要清理时用 `reset-session.mjs`（它也走连接模式）。

实测差异：

```
启动新浏览器 + 导航 + 选会话：6-9 秒
连接常驻浏览器：            34ms
```

常驻浏览器还保留了上一步建立的状态（打开的会话、滚动位置、侧栏折叠），这通常正是下一步需要的。

### 约定四：常驻服务的输出不要轮询

`browser-serve.mjs` 是长期运行的服务，它**永远不会"完成"**。不要用等待任务完成的方式去读它的输出。
需要确认它的状态时，写一个几行的检查脚本连上去问（例如读 `Browser.getWindowBounds`）。

## 事故本身

### 我做了什么

为了让测试快起来，我给 `tools/harness.mjs` 加了 CDP 连接模式：探针不再自己启动浏览器，而是连接到
`tools/browser-serve.mjs` 常驻的那个浏览器。

然后在 `close()` 里写了这么一段：

```js
// 连接模式下不关浏览器，因为浏览器是别人的
if (options.context === undefined && attached === false) await context.close()
```

### 错在哪

`close()` 原本做**两件**事：

1. 关掉浏览器
2. （隐含地）释放掉所有底层资源，让 Node 的事件循环变空，进程自然退出

我只保留了「别关别人的浏览器」这一条，就去掉了第 2 条赖以成立的前提。`chromium.connectOverCDP()`
建立的连接是一个活着的 socket，它会一直占住事件循环。于是：

```
动作跑完 → 浏览器不再被操作 → 连接还开着 → Node 不退出 → 没有输出、没有提示符
```

**我把一个函数的副作用当成了无关紧要的实现细节，直接删掉，又没意识到自己的调用链依赖它。**

### 修法

```js
if (cdpBrowser !== null) {
  await cdpBrowser.close().catch(() => {})   // 断开连接，但不杀浏览器进程
  cdpBrowser = null
}
```

对 `connectOverCDP` 得到的 browser 调用 `close()` 是**断开**，不是杀掉对方进程。断开之后 Node 才能退出。

## 更值得记住的三条规则

### 规则一：任何「打开」都必须有一个保证执行的「关闭」

凡是会占用系统资源的东西——浏览器、CDP 连接、HTTP 服务、文件句柄、终端会话、后台任务——都必须有
确定的释放路径，并且放在 `finally` 里。

**判断标准**：如果这个脚本执行到一半抛异常，进程能退出吗？

我这次的漏点在于：`close()` 里分成「要不要关」和「要不要释放」两件事，我只做了第一件的条件判断，
第二件就跟着一起被跳过了。**正确写法是把两件事分开写**：

```js
try {
  ...做测试...
} finally {
  await browser.close()   // 无条件：内部自己决定关不关浏览器，但一定断开连接
}
```

### 规则二：脚本必须有硬超时，不能靠「它应该会结束」

现在 `openBrowser()` 里加了兜底：

```js
const hangGuardMs = Number(process.env.QC_PROBE_TIMEOUT_MS ?? 180000)
hangGuard = setTimeout(() => {
  console.error('[harness] HUNG: ...')
  process.exit(3)
}, hangGuardMs)
```

关键是**这个 timer 故意不 `unref()`**：它必须在有其他东西占着事件循环时仍然能触发。如果 `unref()` 了，
它就会和进程一起被「别人占着循环」这件事拖住，等于没写。

配套习惯：

- 后台任务超过 2 分钟没动静，先怀疑「脚本没结束」而不是「脚本还在算」
- 长任务里打印阶段标记（`console.log('阶段二：拖动')`），这样从输出就能看出它停在哪一步

### 规则三：先验证最小单元，再搭复杂结构

这次真正的浪费不在那个 socket，而在**在一个没验证过的拖拽实现上反复搭测试**。

我的历史错误是这样累积的：

| 我以为 | 实际 | 怎么错出来的 |
|---|---|---|
| 宽度只有 824 / 640 两档 | 连续可调，每步 20px | 每次都拖到极限，于是只看到两个端点 |
| 只有右侧分隔条有效 | 两侧都有效 | 同上，拖的时候已经在极限 |
| 滚动位置会随机漂移 | 拖动导致重排，`scrollTop` 随之变化 | 没在拖动过程中采样 |

三个结论全部来自「一次性拖到底 + 只测首尾」，而**没有一次实现过连续拖拽 + 逐步采样**。

后来补做的一次基础调研（`tools/explore-drag.mjs`，8 秒跑完）就把三个错误结论全部推翻了：

```
右边柄左拖: 806, 786, 766, 746, 726, 706, 686, 666, 646, 640   ← 连续
左边柄右拖: 810, 792, 776, 760, 742, ...              640   ← 也有效
拖动中 scrollTop: 1476 → 1501 → 1526                        ← 确实会变
```

**教训**：在写任何依赖「拖拽」「滚动」「定位」的测试之前，先花一分钟把那个原语单独跑通，
打印出真实数值。不要把自己对机制的猜测当成已知条件。

## 提速：浏览器只启动一次

这也是这次事故的起因（我为了提速而改动），所以结论保留。

改造前，每一轮测试启动**两次**浏览器：

```
node tools/reset-session.mjs <url>    ← 启动浏览器 → 清理 → 关闭
node tools/probe-xxx.mjs <url>        ← 再启动一次 → 导航 → 等会话列表 → 点会话 → 等 2 秒
```

单次 6-9 秒，一天跑了三十多轮，等于启动六十多次浏览器。

改造后：

```sh
# 终端里常驻一次，不退出
node tools/browser-serve.mjs "<tokenised url>"

# 之后所有探针都复用同一个浏览器
set QC_CDP=http://127.0.0.1:9222
node tools/probe-xxx.mjs <url>
```

实测：

```
attach + goto: 34ms      （原来 6-9 秒）
单次探针总耗时: 0.3s
页面状态保留: 会话已打开、滚动位置、侧栏状态
```

`goto()` 在连接模式下会比对当前 URL，相同则**跳过重新导航**——因为重新导航会把上一步辛苦建立的状态
（打开的会话、滚动位置、折叠的侧栏）全部清掉。

## 给以后的检查清单

写测试脚本之前，逐条过一遍：

- [ ] 这个脚本会不会打开资源（浏览器 / 连接 / 服务 / 文件）？每一样都有 `finally` 释放吗？
- [ ] 如果中途抛异常，进程能退出吗？
- [ ] 有没有硬超时？超时了会打印可诊断的信息吗？
- [ ] 依赖的界面原语（拖拽、滚动、点击）我**单独验证过**吗？数值打印出来看过吗？
- [ ] 这个测试是「一次拖到底看结果」还是「逐步采样」？需要过程数据的场景必须逐步采样。
- [ ] 重新跑一次要多少秒？能不能复用已有状态？
- [ ] 失败时的输出能不能让我**不看代码就知道断在哪一步**？
